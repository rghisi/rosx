# Boot plan

## Invariants

- The kernel schedules exactly `kstatsd` and `init`; init's argv is a `system::boot_plan` script, at most 15 steps and 512 bytes.
- Every program token names its source: `rom:<name>` or `/path`; a token with no source panics the builder at add time and decodes `Malformed` in init.
- Failure policy is log-and-continue; a failed `exec` falls through to the next step, so plans end `exec /shell` then `exec rom:shell`.
- Both arch ports boot the same plan.

## Design

**Boot plan** — the kernel schedules exactly `kstatsd` and `init`, and init's argv is a `system::boot_plan` script assembled by the arch `main.rs` with the fluent `BootPlan` builder. One argument per step: `service <program> <probe>` launches the program and retries `ipc_connect` until the service binds (~10 s budget), `run <program> [args…]` waits the tool's completion future, `exec <program> [args…]` is the hand-off after which init terminates. A `service` step watches that program's completion future while it probes: a service that dies before it binds is reported at once (`[INIT] <NAME> service exited before ready`) and the plan moves on, instead of spending the whole probe budget on a process that is already gone. Every program token declares its source: `rom:<name>` reads a ROM entry, `/path` reads a VFS file through the typed client's size-bounded `read_whole` (a mid-boot mutated image fails as truncated, like the shell launcher), and a bare name is implicit-ROM — valid grammar, used by no shipped plan now that both ports boot the disk. A token that names no source panics the builder at add time and decodes `Malformed` in init. A failed `exec` does not end the plan: init falls through to the next step, so a disk-booting port ends `exec /shell` followed by `exec rom:shell` and still reaches a shell when the disk or its binary is missing. Plans stay inside the argv transport (argv0 plus ≤ 15 steps, ≤ 512 bytes; the builder asserts the bounds at encode). Failure policy is log-and-continue — `[INIT]` diagnostics always lead on to the shell. The arch ports use the protocol crates' `wire::SERVICE_NAME`/`SOURCE_NAME_*` constants as the probe strings for the five protocol-owned services, blockd's coming from `block_protocol::manager::wire`. The shared plan (identical on x86_64 and x86_32): `rom:atad`, `rom:blockd`, `run rom:attach ATA`, `rom:vfsd`, `rom:inputd`, `rom:ps2d` — the ROM bootstrap — then `run rom:mount ata0d0p0 /`, then `service /randomd RANDOM`, `service /echo BULKECHO`, `service /pong PING`, `service /pcid PCI`, `service /ne2kd NE2K` sourced **from the mounted volume**, then the `/shell` → `rom:shell` hand-off pair; a missing disk leaves the services `not available` and lands on the ROM shell.
