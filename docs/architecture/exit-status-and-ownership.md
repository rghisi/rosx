# Exit status and future ownership

## Invariants

- A task's exit status rides its paired completion future, never the `Task`; the future is self-contained and stays valid after the task slot is freed and recycled.
- `Kernel::terminate_with_status` stamps and notifies the completion future before touching any child resource, in the same registry borrow that wakes waiters.
- The status wire is an `i32` owned by `system::exit` (reason in bits 31..24, 24-bit code); user space can only carry `Clean` codes and the panic request code maps to `Panicked(0)`.
- Exit reasons are `Clean`, `Panicked` and `Interrupted`; user space can only carry `Clean` codes.
- `Kill` (syscall 42) terminates another task through its completion-future handle; it refuses the caller and any `Running` target, and stamps `Interrupted(0)` before any teardown.
- `WaitFuture` consumes a future once; a second waiter gets `FutureAlreadyConsumed`, never a kernel panic.
- Every future registry slot carries a `FutureOwner`; a loaded-image group forfeits its unreaped reports when its last live member terminates (`FutureRegistry::reclaim_group`).
- Ownership is a cleanup net, not access control.

## Design

**Exit-status channel** — a task's exit outcome rides its paired completion future, never the `Task` (the scheduler frees the arena slot at termination). The future is self-contained: its completion is its own flag stamped together with the status, never polled from task state — so it stays valid and completed after the task slot is freed and recycled. The wire is an `i32` owned by `system::exit`: reason in bits 31..24 (`Clean`/`Panicked`/`Interrupted`; reserved reasons decode honestly), 24-bit code; `status_for_exit_request` remaps the reserved `EXIT_CODE_PANIC` request code to `Panicked(0)`, so user space can only ever carry `Clean` codes and out-of-range codes are refused (`ExitCodeOutOfRange`). The `Exit` syscall (number 4; number 9 is reserved and unused) diverges through `Kernel::terminate_with_status`, which stamps and notifies the completion future before touching any child resource (state transition, port revoke, group reclaim), in the same registry borrow that wakes waiters — a waiter can never observe completion without its status, and a late waiter consumes it while the issuing group lives; group teardown forfeits unreaped reports (see future ownership). `elf_task_wrapper` maps main's return to `Clean` (high bits masked, no one to report to); `Spawn`/kernel `FunctionTask` keep `Clean(0)`; the usrlib panic handler prints and exits with the panic code instead of `loop {}`, so a dead daemon terminates and wakes its watchers. Delivery is the `WaitFuture` out-ptr (symmetric to the IPC payload) and consumes the future once — a second waiter gets `FutureAlreadyConsumed`, never a kernel panic; usrlib decodes the wire into the `ExitStatus` view (`wait_for_exit_status`), keeping the "parent" as whoever holds the completion-future handle. The shell reports anything but clean zero (`exiter exited with code 3`, `snake panicked`); `exiter` and the `exit_status` suite prove all three origins (main-return, `Exit`, panic redirect) on both arches.

**Task kill** — the `Kill` syscall (number 42) terminates another task through its completion-future handle: kill authority belongs to whoever holds the handle (the launcher), so no new identity surface is needed. `Kernel::kill_task` resolves the handle to its owner task (`TaskCompletionFuture::owned_by` stamps the owner at pairing time; a handle that is not a live completion future is `TaskKillTargetTerminated`), refuses the calling task itself and any `Running` target (`TaskKillTargetRunning` — kill only reaches Ready/Blocked tasks, and the shell never kills the console it runs on), then follows the `terminate_with_status` ordering invariant: stamp `Interrupted(0)` and notify the completion future **before** any teardown (state → Terminated, `discard_waiter` evicts the victim from every future-waiter list so a blocked kill can never be resurrected, port grants revoked, the `FutureRegistry::reclaim_group` + `release_group_allocations` pair runs if the victim was the last live member, scheduler `handle_termination`). The `spinner` app is the deterministic never-exiting carrier; the `ctrl_c` integration suite proves kill-of-foreground, bare-prompt and partial-line `^C`, and that background jobs are spared, on both arches. Known deferred cleanup (victim's IPC connections surviving its death) is logged in `plans/ctrl-c-impl.md`.

**Future ownership = loaded-image groups** — every registry slot carries a `FutureOwner` (`Group(GroupId) | Kernel | Free`) in an `owners` table parallel to the arena: `register(future, owner)` stamps it from the owner derived once at the syscall edge, `consume_inner` clears it to `Free`. The completion future belongs to the *spawning* group (zombie rule: the parent must reap, parent death forfeits the report — a child's stamp targets a swept generation and no-ops), receive futures to the receiving group, waitsets to the creating group (attached children keep their own owners); boot loads and `kstatsd` are `Kernel`-owned and never swept. The last-live-member gate in `terminate_with_status` calls `FutureRegistry::reclaim_group` beside `release_group_allocations`: the dying group forfeits its unreaped reports — parked cross-group waiters wake and consume to the existing honest error (`FutureAlreadyConsumed`, `WaitsetNotFound`), stale mailbox/`parents_of`/TaskRecord references die at the generation check, and slots return to the pool. Blocked == live: a group cannot die while one of its members is parked, so a sweep never wakes a same-group sleeper. Ownership is a cleanup net, not access control: a token holder keeps consumption rights while the owner lives. `apps/leaky` plus the `future_ownership` suite are the leak witnesses; registry exhaustion (a live group hoarding slots) stays possible until the trigger-gated quota lands.
