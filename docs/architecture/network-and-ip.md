# Network and IP

## Invariants

- Ethernet semantics live in `ne2kd` and L3 semantics in `ipd`, the single ARP/IPv4 authority above `ne2kd`; the kernel contributes only grant-mediated port I/O and IRQ events.
- Event RX follows the level-triggered discipline: the daemon re-arms its line with `IrqClear` only after clearing the NIC ISR.
- A pushed `UserDataHandle` must stay parked in a bounded per-owner FIFO until the client reads it; dropping the handle releases the kernel object.
- A serve loop must retain its accept futures across waitset iterations; a dropped pending future swallows its message.
- Every clock reading enters the `ipd` stack core as a `now_ms` parameter, so frame transcripts are provable on the host.
- `ip` configuration is manual by decision; v1 names UDP, TCP, fragmentation, multicast and IPv6 as non-goals.

## Design

Network architecture — Ethernet command semantics live in the user-space `NE2KD` daemon (`ne2kd`) over `net-protocol` (binding `"NE2K"`), mirroring the disk stack's layering: the DP8390 register sequence lives in `ne2kd::dp8390` behind a mockable `NicBus` (a QEMU-faithful `Ne2000Sim` pins the hardware truth in unit tests), the kernel contributes only grant-mediated port I/O. Discovery: PCI RTL8029AS (`10EC:8029`) via `pcid` (the sole holder of 0xCF8–0xCFF; `Find`/`List`/`Enable` treaty, `Enable` sets the I/O-space bit and returns the refreshed slot), ISA fallback at 0x300 (then 0x280), IRQ 9. Event RX: the daemon binds `"IRQ<n>"` and `IrqSubscribe`s, serves a waitset over the service accept + the event accept, and re-arms the line with `IrqClear` after clearing the NIC ISR (level-triggered discipline — see Interrupt discipline). The `ne2k` CLI auto-launches `pcid`+`ne2kd` detached (`load_with_args`, completion handle dropped) when their bindings are absent — the shell itself blocks on launched programs, so daemons never come up from a prompt; both daemons are boot-plan services sourced from the mounted volume (`/pcid`, `/ne2kd`), not ROM entries. The `arp` CLI is a raw-frame diagnostic client of the same daemon: `arp watch [secs]` decodes every frame off the poll queue (ARP lines, foreign EtherTypes skipped, malformed named, tally at the deadline), `arp who-has <tip> [from <sip>]` broadcasts a request and prints the first matching reply within 5 s, `arp respond <ip> [secs]` answers requests for that IP unicast, `arp announce <ip>` sends a gratuitous reply. The NE2K face has an RX subscription: `Watch` (opcode 0x05) registers a connection and the event drain fans every frame out as a `PushFrame` notice beside a data object — watchers and the poll queue both receive, so poll clients keep byte-identical semantics — with `watch_pushes`/`watch_drops` counted. It is the in-tree first unsolicited server→client push (`ne2k watch [count]` is its client) and it carries two daemon disciplines: a pushed `UserDataHandle` must stay parked in a bounded per-owner FIFO because dropping the handle releases the kernel object before the client reads it, and a serve loop must retain its accept futures across waitset iterations (a dropped pending future swallows its message — there is no FutureDrop syscall). The Ethernet + ARP codec lives in `net-protocol` (the `ethernet` and `arp` modules, host unit-tested), alongside the total `ipv4` and `icmp` codecs the same theme owns. QEMU wiring: `attach_ne2k_pci` passes an explicit `user` netdev (QEMU gives a bare `-device ne2k_pci` no backend), so slirp itself answers `arp who-has 10.0.2.2` from its proxy MAC — a single-guest ARP proof on `cargo xtask run`; the guest-pair and watch tests share a `socket` mcast netdev like the ne2k ones, and the watch test injects frames from a host UDP socket into that group (the medium loopbacks TX back to the sender and to any host member joined on the group port — a witness socket with `SO_REUSEADDR` + `IP_ADD_MEMBERSHIP` sees every frame the guests put on it).

IP architecture — IP command semantics live in the user-space `IPD` daemon (`ipd`) over `ip-protocol` (binding `"IP"`), the single ARP/IPv4/L3 authority above `ne2kd`. The stack core is a mock-tested library inside `apps/ipd`: `FrameDevice` + `MockDevice`; `ArpCache` (600 s TTL, 1 s × 3-attempt bounded resolve, one coalesced flight per target, snapshot for `Neigh`); ethertype demux, ARP learn-from-any-frame and who-has answer, IPv4 checksum verify with destination and fragment filters, ICMP echo answer, direct-or-gateway forwarding with resolve-before-send, and a 1500-byte datagram ceiling; every clock reading enters as a `now_ms` parameter, so exact frame transcripts are proven on the host before any VM boots. The daemon attaches `ne2kd`'s Watch as its device — TX pads frames to 60 and sends them through the NE2K `Send`, parking each data object until its matching Ack reaps it (Send acks and Watch pushes share one mailbox consumed by one arm) — and fans `Datagram`/`Unreachable` events out to `Subscribe`d clients with an ICMP-kind filter. The client face is raw push: subscribers receive datagram payloads as data objects beside a `PushDatagram` notice and decode ICMP through `net-protocol` — `ip ping` is a client, not a stack feature. The `ip` CLI (`status` / `config <addr>[/len] [gw <addr>]` / `neigh` / `ping <addr> [count] [size]`) auto-launches `pcid`+`ne2kd`+`ipd` the way `ne2k` does; configuration stays manual by decision — no boot-plan step, no ROM entry, no kernel changes — and v1 names UDP/TCP/fragmentation/multicast/IPv6 non-goals. The ICMP client lives under `ip ping` because `ping` is taken by the IPC bulk demo (`/pong`). Proofs on both arches: `ip_inject` (host witness on the mcast group asserts the `is-at` and echo-reply bytes of crafted who-has and echo-request frames), `ip_slirp` (`ip ping 10.0.2.2` answers — the first in-tree evidence that slirp replies to guest ICMP echo); the two-VM `ip_pair` ping test was removed with the multicast pair tests (`docs/decisions/integration-drop-pair-spike-and-bench-tests.md`).
