# x86_32 → i486 — making 486 compatibility a maintained invariant

> **Status:** Proposed. Written 2026-11-02 at worktree `playful-falcon`, HEAD `50cd060`.
> **Goal:** the x86_32 port runs on Intel 486-class CPUs (the oldest x86 with real atomic
> instruction support: `CMPXCHG`/`XADD`), and — more importantly — *stays* 486-clean as code,
> optimizer and toolchain drift. Then extend the boot path so a real 486 board can boot it.
> **Method:** every code fact below is cited to a path (and line) re-verified against this tree;
> every runtime fact was measured on this machine (QEMU 10.2.1, rustc 1.101.0-nightly
> `0abfedbc7` 2026-10-02). Measured observations are marked **[O]**. Facts this plan cannot prove
> are marked **unverified** and routed to the milestone (or to real hardware) that must prove them.
> Repo law applies throughout: `kernel/` stays `no_std` and arch-agnostic, **no comments ever**
> (assembly excepted), unit tests for kernel modules, no test-only production surface,
> `cargo build --workspace` stays forbidden, commit subjects are bare imperative (no prefix).

---

## 0. Goal & Non-Goals

### Goal
- The build *guarantees* a 486-safe instruction set: the compiler baseline is pinned so that
  no future refactor or nightly bump can silently emit a 586+ instruction.
- QEMU + CI enforce it: the x86_32 run and test path boots under the pinned 486 CPU model, and a
  disassembly audit gate catches what TCG cannot.
- Real-hardware boot is plausible: a Multiboot v1 kernel that GRUB Legacy/GRUB 2 of the 486 era
  can load, with memory detection that does not assume a bootloader-provided mmap buffer.
- The discipline that keeps it working (no FP, no CPUID-based feature probing, 32-bit atomics)
  is written down where regressors will read it (AGENTS.md).

### Non-Goals
- No 386 support. Pre-486 has no `CMPXCHG`/`XADD`/`XCHG-lock`; the scheduler, future registry and
  IRQ-guard discipline would all need interrupt-masked atomics. Explicitly out of scope.
- No 486SX target in v1 (kept *open* as DECISION D1): SX lacks the FPU (harmless today — O2 shows
  zero x87) but also lacks `CMPXCHG8B` (also unused). SX only becomes mandatory if we choose it.
- No bespoke bootloader this iteration; the GRUB/Legacy path is the real-hardware story, a RosX
  MBR loader is a candidate follow-up plan.
- No FPU state save/restore, no floating point anywhere. Zero-FP is a load-bearing invariant
  (F5), guarded by M3's audit, not changed here.
- No APIC, no PCI, no DMA, no real-time clock (CMOS) driver — the 486 baseline is PIC + PIT +
  PIO-IDE, which is exactly what the port already is.
- No x86_64 changes. That port keeps its richer baseline; the audit gate is x86_32-scoped.

## 1. Verified baseline facts

### Code facts (cited against `50cd060`)

- **F1** `arch/x86_32/rosx-i686.json:13` and `arch/x86_32/rosx-i686-user.json:13` disable only
  `-mmx,-sse,-sse2` on `llvm-target: i686-unknown-none`. LLVM's i686 baseline includes
  **+cmov, +cx8, +fxsr** — features from Pentium/P6-era CPUs (or 486DX for `cx8`). Today's binary
  is 486-clean by *optimizer luck*, not by guarantee: a refactor or a nightly bump may emit
  `cmov`/`fxsave` at any time and brick the kernel on hardware — silently, because QEMU's default
  CPU model accepts all of it (F8).
- **F2** Every atomic on the x86_32 path is ≤ 32 bits wide: `AtomicUsize/U32/U8/Bool/Ptr/I32`
  (`kernel/src/irq_guard.rs:3`, `memory/free_list_allocator.rs:3`, `task.rs:10`, `once.rs:3`,
  `usrlib/src/runtime.rs:6`, `arch/x86_32/src/interrupts.rs:2`). `AtomicU64` appears only under
  `arch/x86_64/`. So the 486's atomic repertoire (`LOCK XCHG/ADD/AND/OR/SUB/DEC/INC`, plus the
  486-introduced `CMPXCHG`/`XADD`) covers 100% of usage; `CMPXCHG8B` is not needed.
- **F3** No `cpuid`, `rdtsc`, `rdmsr/wrmsr`, APIC or paging code in `arch/x86_32/`, `arch/x86-generic/`
  or `kernel/` (grep-verified). `arch/x86_32/src/boot.S` sets no CR0/CR4 bits, enables no paging:
  flat protected mode throughout — no PSE (Pentium), no PAE, no global-pages dependency. The IDT
  (`interrupts.rs`) is 8-byte 32-bit gates + `iretd`; the syscall path is `int 0x80`
  (`cpu.rs:170-195`, `usrlib/src/arch/x86_32.rs:5`). All 386-era mechanism.
- **F4** `arch/x86_32/src/boot.S:5` is a Multiboot **v1** header (`0x1BADB002`); `main.rs` parses
  the v1 info struct. (AGENTS.md says "Multiboot2/GRUB" — wrong, and the fix in M6 matters:
  v1 is precisely what 486-era bootloaders speak. GRUB 2 loads it via its `multiboot` command;
  the runner's GRUB config (`x86-runner/src/lib.rs:152`) already uses `multiboot`.) `_start`
  installs the kernel's own flat GDT (`lgdt` + far-`retf` CS reload + data segments, added by
  `50cd060`) so the loader's descriptor layout is no longer assumed — all 386-era mechanism, and
  a real derisking of the GRUB-Legacy path (M5).
- **F5** Zero floating-point usage across the workspace: no `f32`/`f64` in `kernel/`, `usrlib/`,
  `apps/` (grep-verified); objdump of kernel + user ELFs shows zero x87/SSE instructions (O2).
  `swap_context` (`cpu.rs:126-146`) saves GPRs only — correct *only while* FP stays absent. If any
  app ever computes in floats, task-switched FPU state (FSAVE/FRSTOR + CR0.TS) becomes mandatory,
  and on a 486SX it becomes an emulator conversation. This invariant must be machine-guarded (M3).
- **F6** Timekeeping is PIT-based: `SYSTEM_TIME_MS` (AtomicU32) advanced by the 100 Hz PIT tick
  (`interrupts.rs:6,21-23,158-163`). No TSC dependency anywhere on the 32-bit path — important,
  because the 486 has no `RDTSC` (Pentium).
- **F7** ATAD's port trait surface is byte + 16-bit word only (`apps/atad/src/taskfile.rs:46-48`,
  `main.rs:23-35`): the era-safe IDE PIO mode. The mediated `PortIo` executor offers dword
  accesses (`x86-generic/src/port.rs:57,79`) but no disk driver uses them. 32-bit data-register
  I/O is the classic 486-era IDE corruption trap; staying 16-bit avoids it by construction.
- **F8** `x86_runner::qemu_command` (`arch/x86-runner/src/lib.rs:170-197`) passes no `-cpu` flag:
  QEMU runs its default CPU model, which happily executes 686 instructions. The integration
  harness consumes the *same* function (`tests-integration/src/qemu.rs:53,85`), so one change
  there gates dev runs, the full `x86_32` test suite **and** the ISO-boot test simultaneously.
- **F9** `parse_memory_map` (`arch/x86_32/src/main.rs:113-151`) returns **zero usable regions**
  unless Multiboot flags bit 6 (mmap buffer) is set (line 124). QEMU's multiboot loader provides
  mmap, so the gap is invisible in QEMU. GRUB Legacy — the realistic 486-era bootloader —
  typically supplies only `mem_lower`/`mem_upper` (flags bit 0, offsets 4/8): booting a real 486
  through it today would yield a kernel with **no heap**. Latent, real, must-fix (M4).
- **F10** Three `pause` instructions exist in the shipped kernel binary, inlined from
  `core::hint::spin_loop()` (`kernel/src/once.rs:66`, the `Once::get_or_init` contention loop).
  LLVM emits PAUSE regardless of `-march`; it cannot be compiled away. PAUSE is P6-era, executed
  as a NOP on earlier CPUs (Intel SDM: reserved, treated as NOP; QEMU's 486 model confirms — O2
  boot ran the VGA `write_str` spin loop thousands of times under `-cpu 486` without faulting).
  Accepted risk; the only hardware-verification item at the instruction level.
- **F11** User-space target is PIE/PIC (`rosx-i686-user.json:14-15`). PIC codegen is pure integer
  (call/pop thunk + GOT arithmetic) — era-safe once the same feature pin lands (M1 proves, O4).
- **F12** CI already has `build-x86_32` and `test-x86_32-integration` jobs
  (`ci.yml:61-115`) and the artifacts pipeline builds the GRUB ISO
  (`build-artifacts.yml:38-78`, needs `grub-mkrescue` + `xorriso` + `mtools`). The audit gate (M3)
  is a step in the existing job — no new job shape needed. `50cd060` also landed an
  ISO-booting integration test (`tests-integration/tests/iso_boot.rs` + `BootMedium::CdImage`),
  i.e. the GRUB boot path now has a QEMU regression test that M2's CPU pin will cover.

### Measured runtime facts **[O]** (this machine, 2026-11-02)

- **O1** Disassembly of the shipped x86_32 kernel (release, `-cpu 486`-relevant mnemonics;
  re-verified on `50cd060`):
  `cmov*` 0, `cmpxchg8b` 0, `cpuid` 0, `rdtsc` 0, `fxsave/fxrstor` 0, SSE/MMX/x87 0. Lock ops
  present: `lock cmpxchg` ×8, `lock xadd` ×10, `lock decl` ×12, `lock add/addl/sub/incl` ×4 — all
  486-class. Same audit of `shell`, `vfsd`, `atad`, `pi` ELFs: zero hits. Sole exception: `pause`
  ×3 (F10).
- **O2** `qemu-system-i386 -cpu 486 -kernel target/rosx-i686/release/rosx-x86_32` boots the full
  stack: mmap parsed, `[KERNEL] Starting`, all eight service banners, `rose>` prompt, and the BULK
  self-test completes (re-run green on `50cd060`, own-GDT boot.S included). The 486 model runs the
  current kernel end-to-end.
- **O3** **The `-cpu 486` gate is real.** A hand-linked multiboot probe executing one `cmovl`
  traps exception 6 (`#UD`) under `-cpu 486` (verified with `-d int`), escalating to triple fault.
  TCG gates `cmov`/`cmpxchg8b`/SSE on CPUID feature bits, so booting under `-cpu 486` genuinely
  validates. Two blind spots remain: `cpuid` *always* works under QEMU (never traps), and the
  earliest 486 steppings lack the instruction entirely → instruction-set regressions of that kind
  need the objdump audit (M3), not QEMU.
- **O4** **The toolchain fix is proven end-to-end.** Adding `-cmov,-fxsr` to both specs' feature
  strings (the only edit) and running the full `cargo xtask build x86_32`: `core`/`alloc`/
  `compiler_builtins` via `-Z build-std`, kernel, all apps — zero errors, ~23 s. The rebuilt
  kernel + shell show zero 586+ mnemonics and boot under `-cpu 486` exactly as before (O2).
  The edit was reverted after measuring; this plan's M1 lands it properly.
- **O5** Footprint: kernel ELF 1.07 MB (embeds the roster ELFs), `rom.img` 629 KB. Boards with
  4–16 MB — era-typical 486 memory — are comfortably in range; nothing hardcodes a lower bound.

## 2. Decisions (owner, before the milestones they gate)

- **D1 — DX or DX+SX?** DX-only keeps `cx8` in LLVM's baseline (486DX has `CMPXCHG8B`); SX support
  adds `-cx8` to the feature strings. Nothing in the tree uses 64-bit atomics or FP, so SX costs
  nothing today beyond pinning it before something does. **Recommendation: pin `-cmov,-fxsr` now
  (needed either way) and additionally pin `-cx8`** — it is free insurance; revisit only if an
  AtomicU64 ever appears on a 32-bit path. Gates M1. (O4 proved the `-cmov,-fxsr` combination;
  the `-cx8` variant is proven by M1's own build gate.)
- **D2 — rename i686 → i486?** The specs, target dir names (`rosx-i686`, `rosx-i686-user`),
  `ArchSpec` fields and CI upload paths all say i686. Renaming is cosmetic churn (~15 references)
  that makes the invariant visible at every layer. **Recommendation: defer**; rename in a later
  hygiene pass once the invariant is enforced, to keep this plan's diffs surgical. Gates nothing.
- **D3 — real-hardware boot media.** Options, in increasing effort: (a) document the manual
  recipe (copy the multiboot ELF to a GRUB-equipped IDE disk/CF adapter; GRUB Legacy or GRUB 2
  both load F4's v1 header); (b) `cargo xtask image x86_32` gains a raw-MBR-disk-image mode via
  `grub-install` (needs loop devices — fine on CI with sudo, awkward on every dev box); the
  `BootMedium::CdImage` + `iso_boot.rs` pattern from `50cd060` is the ready-made precedent for a
  `DiskImage`-medium QEMU verification;
  (c) a RosX bespoke MBR loader (separate plan — the educational capstone, not a prerequisite).
  **Recommendation: (a) now, (b) only if (a) proves annoying on real hardware.** Gates M5.

## 3. Gap A — Pin the compiler baseline (M1)

Edit F1's two lines: kernel spec features become `-mmx,-sse,-sse2,-cmov,-fxsr`
(+ `-cx8` per D1); user spec likewise. Nothing else — the JSON specs are already the single
feature authority, and build-std rebuilds `core` with them (O4).

Why these: `CMOVcc` = P6-era (Pentium Pro); `FXSR` (`fxsave/fxrstor`) = P6/AMD-K6-era; `CX8`
(`cmpxchg8b`) = 486DX. Disabling them moves LLVM's codegen floor to 486 for every crate in the
graph, including our own inline-asm-free kernel and the PIC user ABI (F11).

**Gate:** `cargo xtask build x86_32` green; O1's mnemonic audit re-run over kernel + every user
ELF shows zero hits (pause excepted, F10); `-cpu 486` boot reaches the prompt (O2 re-run);
`cargo xtask test --skip-integration` green; x86_64 untouched.

## 4. Gap B — Boot every x86_32 QEMU session on the 486 model (M2)

`x86_runner::qemu_command` (F8) gains the CPU pin on the x86_32 arm: `-cpu 486` (exact QEMU model
name). Because the integration harness routes through the same function (`tests-integration/src/
qemu.rs:54`), `cargo xtask run x86_32`, `cargo xtask image x86_32`'s verification path, and the
whole `ROSX_ARCH=x86_32` suite immediately run on the pinned model — O3 proves it catches
cmov/cmpxchg8b/SSE regressions that the old default-CPU runs would silently swallow.

Runner unit tests (`lib.rs` tests module, e.g. `x86_32_runs_from_the_multiboot_kernel_itself`
at line 245 and the `CdImage` test at 278) extend to assert the `-cpu 486` arg pair. x86_64's
command shape is unchanged (no `-cpu` there); its tests unchanged. One honest side effect: the
ISO-boot test (F12) then boots GRUB's core.img under the emulated 486 too — expected fine
(SeaBIOS + GRUB are 486-class), but M2's gate must *show* it, not assume it.

**Gate:** the full `ROSX_ARCH=x86_32 cargo test -p tests-integration -- --test-threads=1` suite
green under the pinned model; `cargo run -p rosx-x86_32` interactive boot green; x86_64 suite
untouched and green.

## 5. Gap C — Disassembly audit gate (M3)

QEMU-TCG's gate (O3) has two permanent blind spots: `cpuid` never traps under QEMU, and feature
bits for exotic instructions are unevenly checked. The belt to TCG's suspenders is a static audit
of the *shipped artifacts*: a new `cargo xtask check-isa x86_32` (new module in the `xtask` host
crate) that runs `objdump -d` over the kernel ELF + every user ELF + shell, and fails on any
mnemonic outside the 486-safe set. Design notes:

- Rejection list (first token of the instruction, after any `lock` prefix): `cmov*`,
  `cmpxchg8b`, `cpuid`, `rdtsc`, `rdmsr`, `wrmsr`, `fxsave`, `fxrstor`, `syscall`, `sysenter`,
  `xgetbv`, `wrfsb32`, `invpcid`, plus every SSE/MMX/x87 mnemonic (the x87 term doubles as the
  F5 no-FP guard). `pause` explicitly allowed with F10's rationale recorded in this plan, not in
  code comments.
- The scan is a pure string→classification function over `objdump` text lines — unit-tested with
  embedded fixture snippets (repo law: unit tests, no test-only surface; the command itself is the
  production caller).
- Host dependency: binutils `objdump` (already an implicit CI prerequisite via the rust toolchain;
  the xtask probes and reports cleanly, same pattern as the GRUB tooling probe in `image`).
- CI: one added step in the existing `build-x86_32` job after the build (F12). The audit also runs
  locally pre-push by whoever wants it; CI is the enforcement point.

**Gate:** `cargo xtask check-isa x86_32` green on the M1+M2 tree; a deliberately poisoned temp
copy (one `cmov` via `-Ctarget-cpu=i686` rebuild of one app) makes it fail loudly in a unit/CI
trial; x86_64 job unaffected.

## 6. Gap D — Memory detection without assuming mmap (M4)

F9's gap is the one true latent *functional* bug on real 486 hardware. Fix in the shared family
crate so it is host-testable: new `x86-generic/src/multiboot.rs` owning the v1 info-struct decode
(flags, mmap walk, `mem_lower`/`mem_upper` fallback), consumed by `arch/x86_32/src/main.rs`
(and optionally later by x86_64's identical parser — out of scope here).

Semantics: if bit 6 set → current mmap walk (unchanged, `main.rs:128-148`). Else if bit 0 set →
regions `[0, 1 MiB)` (from `mem_lower`) and `[1 MiB, 1 MiB + mem_upper KB)`; `trim_to_safe_memory`
(`main.rs:95-111`) already removes the part the kernel occupies, and the 1 MiB split is the
Multiboot load-address convention. Else → no regions, same as today (bootstrap's existing
empty-blocks behavior — no invented defaults). The `x86_32` `main.rs` shrinks to a call; the
mmap entry layout stays documented by the parser's own tests, not comments.

**Gate:** host unit tests green (`cargo test -p x86-generic`): mmap path, mem_upper-only path,
neither path, malformed flags. Full x86_32 integration suite green in QEMU (mmap path — the
fallback path is *unverified* until GRUB Legacy on real hardware or a GRUB-Legacy-booted QEMU
session; marked and routed to M5's hardware checklist). x86_64 untouched.

## 7. Gap E — Real-hardware boot path (M5, gated by D3)

Per D3(a): a short doc note (AGENTS.md "Real hardware" subsection) stating the recipe —
IDE disk/CF with GRUB Legacy 0.97 or GRUB 2, `kernel` + `multiboot` entry, boot. No code.
Its real content is the **hardware verification checklist** this plan cannot execute (each item
**unverified** until run on silicon):

1. `-cpu 486` boot parity expectations vs. real board: GRUB (v1) → memory map banner
   (exercises M4's fallback if the GRUB build lacks mmap — expect `[MEMORY] Total:` on 4–64 MB).
2. PAUSE-as-NOP confirmation (F10) — any `#UD` at first `Once` contention during early boot.
3. PIT 100 Hz / 8259A cascade timing on VLB/PCI chipsets (`SYSTEM_TIME_MS` advances; shell echo).
4. 16-bit IDE PIO on a real drive (atad: identify + LBA read; timing margins, IORDY).
5. VGA text console standalone (no debugcon 0xE9 — writes to the unclaimed port must stay
   harmless; VGA path is the only output).
6. 486SX sub-case (only if D1 chose SX): boot without FPU present.

Per D3(b) if elected: `xtask image x86_32` grows a raw-MBR mode (`grub-install` into a sparse
disk image; document the sudo/loop requirement), verified by booting the image in QEMU
(`-hda`, `-cpu 486`), never by assumption.

**Gate:** recipe documented; every checklist item either executed on hardware (owner's run) or
explicitly marked open. No gate may be marked green without hardware evidence.

## 10. Threat register

| Threat | Blast radius | Mitigation in this plan |
|---|---|---|
| Nightly bump re-enables a forbidden mnemonic (JSON feature drift, build-std change) | silent on QEMU, fatal on hardware | M1 pin + M3 audit in CI is exactly this alarm |
| Custom target JSON format churn (`-Z` instability) | build breakage only (loud) | specs are two files; failure mode is a build error, not a hardware brick |
| Someone adds FP in an app | corrupt task state on *all* arches, fatal on 486SX | M3 x87/SSE rejection = machine guard for F5's discipline |
| `AtomicU64` on a 32-bit path | needs `cmpxchg8b` → hard-faults on 486SX, and on DX with `-cx8` pinned it becomes a libatomic link error (loud) | rejection of `cmpxchg8b` in M3; D1 records the choice |
| GRUB 2 on early-486 real boards misbehaves (modern core.img, El Torito absent) | boot fails at firmware stage, invisible to all QEMU tests | F4's v1 header keeps GRUB Legacy 0.97 viable; M5 documents it; hardware is the only judge |
| mmap-less bootloader → zero heap | kernel boots, services fail on allocation | M4 fallback; unit matrix; M5 checklist item 1 |
| PAUSE not NOP on some clone 486 | `#UD` on first `Once` contention (early boot) | F10 accepted-risk note; M5 item 2; mitigation path (route the spin hint through `Cpu`) is one small commit if ever needed |
| TCG ≠ silicon (uneven instruction gating, no bus timing, no IDE quirks) | false confidence | the audit gate (M3) covers static code; M5 exists precisely because QEMU cannot close this |
