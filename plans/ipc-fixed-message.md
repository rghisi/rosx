# Plan — MINIX-style fixed 64-byte by-value message IPC (branch `ipc-capability-handle`, HEAD 362d470)

> **Date:** 2026-10-10 · **Status:** Approved design, not started
> Complements `plans/ipc-capability-handle.md` and `plans/ipc-message-api.md` (house format). All baseline facts below were re-verified read-only against the working tree at HEAD 362d470.

## 1. Objective

Replace the message-handle IPC (create/write/seal/read/dispose + `IpcMessage { message_handle, connection_handle }`) with a MINIX-style fixed 64-byte, by-value message: user posts a `Message` on its stack, the kernel copies it in, validates the connection generational slot, resolves direction by caller-task identity, and enqueues an inline copy into a 32-deep mailbox; `wait_future` gains an `out_ptr` and copies the delivered envelope back into the caller's buffer. Delete `message_buffer.rs`/`message_buffer_manager.rs`, the boxed-`Result`/debox ABI on the IPC path, and `FutureResult` — leaving heap-free, unsafe-free user-side IPC and a register-encoded ABI shared by all IPC-adjacent syscalls.

## 2. Design decisions (a–h)

**a) Syscall numbering — RETIRE 18/19/21/24; keep `IpcSendMessage = 20`, `IpcReceiveMessage = 22`, `IpcAcceptMessage = 23` untouched. No number changes at all.**
Deleted: `IpcCreateMessage`(18), `IpcWriteMessage`(19), `IpcReadMessage`(21), `IpcDisposeMessage`(24) variants + their four `TryFrom` arms. Rationale: with only three syscalls surviving, renumbering 20/22/23 → 18/19/20 buys nothing but three changed enum values, three changed `TryFrom` arms, and a new enum/dispatcher desync surface (the failure mode the previous plan flagged: forgetting an arm compiles clean and silently returns 0); keeping the surviving lines byte-identical removes that surface entirely. Retired numbers fail closed: `TryFrom` → `Err(())` → `Err(_) => 0` (`kernel/src/syscall.rs:124`) — verified above. Holes 13/14/16/17 already existed; contiguity was never a runtime property, only a comment-quality one (and we do not write comments).

**b) `Message` lives in `system/src/ipc.rs` (shared by kernel, usrlib, apps) as a `repr(C)` struct with a packed-`u64` conn field and accessors.**
```rust
pub const MESSAGE_BYTES: usize = 64;
pub const MESSAGE_PAYLOAD_BYTES: usize = 56;

#[repr(C)]
#[derive(Debug, Copy, Clone, PartialEq, Eq)]
pub struct Message { conn: u64, data: [u8; MESSAGE_PAYLOAD_BYTES] }

impl Message {
    pub const EMPTY: Self;                                   // conn: 0, data all zero (const)
    pub fn new(connection: IpcConnectionHandle, data: &[u8; MESSAGE_PAYLOAD_BYTES]) -> Self;  // conn = connection.pack() as u64
    pub fn conn(&self) -> IpcConnectionHandle;               // Handle::unpack(self.conn as usize)
    pub fn data(&self) -> &[u8; MESSAGE_PAYLOAD_BYTES];
}
```
Why this form is the both-arch agreement point: `pack()` returns `usize` (40-bit-bounded on x86_64, 24-bit-bounded on x86_32 — §0 range fact), so widening to `u64` at construction and truncating with `as usize` inside `conn()` is lossless on both arches while the wire/slot bytes are arch-invariant (u64 first ⇒ size 64, align 8, no padding, `[0..8]` = packed handle, `[8..64]` = payload — MD-1 exactly). A stored `Handle` struct would *not* be arch-invariant (`HalfSize` flips u32↔u16), and a bare `[u8; 64]` re-introduces byte-slice plumbing for no gain. Private fields + accessors keep layout knowledge in one crate. No length field anywhere (MD-1).

**c) Mailbox = lazily grown `VecDeque<Message>` with a push-time depth cap of 32 (`MAILBOX_DEPTH`), `push_back` becomes `Result<(), IpcSendError>`; `drain` is deleted.**
Rejected the inline `[Message; 32]` ring: `GenerationalArena::new()` pre-allocates `Vec::with_capacity(S)` of `Option<Mailbox>` — embedding 2 KiB per Mailbox would inflate every manager's arena Vec by ~512 KiB at construction (`IpcManager::new()` at boot **and every `#[cfg(test)]` local manager**), while the VecDeque only ever reaches ~2 KiB when actually full (32 × 64 B = the MD-6 bound) and stays tiny otherwise. Depth is checked as `queue.len() == MAILBOX_DEPTH` at push → `Err(())` at `Mailbox` level; `MailboxManager::push_back` maps mailbox-full → `IpcSendError::ConnectionCongested` (a variant that exists today, `system/src/ipc.rs:24`, currently dead — now wired), mailbox-handle-dead → `IpcSendError::ConnectionNotFound` (unreachable after `send_message`'s liveness check on single-core, kept fail-safe). `drain()` deleted: slots are plain `Copy` bytes, so `MailboxManager::remove` (already called by `disconnect`) dropping the queue is the whole teardown — no handles to dispose (MD-8).

**d) Register-encoded returns — tag bit `IPC_ERR_TAG = 1 << (usize::BITS − 8)`; migrate ALL four return-deboxing IPC syscalls (connect, bind, send, wait) now; keep the `&str` arg-side `Box::into_raw` on connect/bind.**
Encoding (in `system/src/ipc.rs`, so kernel encode + usrlib decode cannot drift):
```rust
pub const IPC_ERR_TAG: usize = 1usize << (usize::BITS - 8);   // bit 56 on x86_64, bit 24 on x86_32
pub const fn ipc_err(code: usize) -> usize { IPC_ERR_TAG | code }
pub const fn ipc_is_err(raw: usize) -> bool { raw & IPC_ERR_TAG != 0 };
```
plus `const fn to_reg(self) -> usize` / `fn from_reg(raw: usize) -> Self` on each error type. **Exhaustive disjointness:** the four tagged registers carry only (i) `0` (send/wait success), (ii) packed handles from the **S=256** connection/bindings arenas ⇒ `< 2⁴⁰` (x86_64) / `< 2²⁴` (x86_32) by the §0 range fact (index seeded `0..255`, generation `HalfSize::MAX`), (iii) `IPC_ERR_TAG | code`, `code ∈ 1..=8`. `2⁴⁰ ≤ 2⁵⁶` and `2²⁴ < 2²⁴` is the tag itself — the packed space and tag space are arithmetically disjoint on both arches; system test asserts `(255usize << HALF_BITS) | (HalfSize::MAX as usize) < IPC_ERR_TAG` with `HALF_BITS = core::mem::size_of::<collections::generational_arena::HalfSize>() * 8`. FutureHandle packed values (registry **S=1024** ⇒ up to `2⁴²−1` / `2²⁶−1`, which CAN set x86_32 bit 24 for indices ≥ 256) **never share a register with the tag**: `IpcReceiveMessage`/`IpcAcceptMessage` return bare handles decoded by `FutureHandle::unpack` with no error possible (§0), and `WaitFuture` returns status only, never a handle — the invariant "decode `IPC_ERR_TAG` only in the connect/bind/send/wait return paths" is stated here and required in Steps F/G. `Exec`/`LoadElf`'s existing `u64::MAX` failure sentinel is a different syscall with a different decoder — untouched, no collision domain.
Per-call error sets (codes local to each syscall number): `IpcConnect` 1=`ServerNotFound`, 2=`ConnectionCannotBeEstablished`; `IpcBind` 1=`AlreadyBound`; `IpcSendMessage` 1=`ConnectionNotFound`, 2=`ConnectionCongested`; `WaitFuture` (message futures only) 1=`ConnectionNotFound`, 2=`NoMessagesAvailable`, 3=`MailboxNotAvailable`. `from_reg` maps unknown code → the enum's first variant (panic-free; unreachable against the matched kernel encoder).
Migration scope decision: connect + bind + wait migrate **now** — (1) `WaitFuture` cannot keep the debox anyway (MD-5 forces its redesign), (2) the shell loop boxes a `Result` per `ipc_connect` × 259 iterations, the hottest IPC path in the integration test, (3) half-migrated usrlib would forbid the "zero `Box::from_raw` in usrlib" grep gate that proves MD-7. Residual, documented: connect/bind still `Box::into_raw(Box::new(service))` the arg `&str` — arg-side, `into_raw` is safe, and removing it needs a string-passing redesign outside the locked syscall set (MD-4); usrlib stays **unsafe-free** (no `from_raw`), heap-free on the *message* path only.
`ipc_disconnect` unchanged (void, returns 0 today).

**e) `WaitFuture`: `arg1 = fh`, `arg2 = out_ptr`; return is `0` on success / `ipc_err(code)` on a message-future error; `FutureResult` and `Future::into_result` are DELETED.**
Which future fired needs no return signal: the caller passed the `fh` and knows its kind statically (the enum existed only because one boxed blob served all kinds). Copy point: inside the `WaitFuture` dispatcher arm, **after** `wait_future` resumes the task (the task is parked in this very frame; §0 `kernel.rs:223-231` — resume continues in-arm). No out_ptr is stored in the future or task context; the register arg is bound to a local (`let out_ptr = arg2;`) **before** blocking so it lives on the task's kernel stack across the park. Arm shape: `Ok(future) => match future.as_any().downcast_ref::<IpcMessageFuture>() { Some(ipc) => match ipc.result() { Ok(m) if out_ptr != 0 => { unsafe { core::ptr::write(out_ptr as *mut Message, m) }; 0 }, Ok(_) => 0, Err(e) => e.to_reg() }, None => 0 }, Err(_) => <keep today's panic semantics — bind with `.unwrap()` as the current arm does>`. Non-IPC kinds hit `None => 0` and never read `out_ptr` (MD-5). Trait surgery: remove `Future::into_result` + `FutureResult` enum; update the four impls (`TimeFuture`, `TaskCompletionFuture`, `DummyFuture` test type, `KeyboardFuture`, `IpcMessageFuture`) — no other callers exist (census: `kernel.rs` `wait<T>` uses `into_any`, `sleep`/`ReadChar` discard; usrlib/apps per Steps G/H). `IpcMessage` struct dies (MD-8); `IpcMessageFuture` survives holding `Option<Message>` (`with_message(Message)`, `result() -> Result<Message, IpcReceiveError>`).

**f) Accept: the envelope `[0..8]` conn field IS the reply address, and this matches the flow unchanged.**
Client gets its conn from `ipc_connect` directly (shell prints `RANDOM Server: {index} {generation}` from that return — untouched, usrlib still re-exposes `Result<IpcConnectionHandle, _>`). A client-sent envelope's conn field is filled by `Message::new(conn, …)` in usrlib `ipc_send`; the kernel passes mailbox bytes through unmodified (by-value enqueue, no re-stamping), so the accepted envelope's `conn()` is exactly that client's live handle; the server replies `ipc_send(envelope.conn(), …)` and direction flips correctly because the caller task is not `conn.client_task` → routes to `client_mailbox` (MD-3, proven by kernel test 2). Validation of the conn field is liveness-only (MD-2): send looks the connection up and resolves direction by `kernel().execution_state.current_task()` — the sender-supplied field never steers routing beyond selecting which live connection object is consulted.

**g) Kernel unit-test matrix (full enumeration in Steps C/D).** stale-conn send rejected; recycled-connection-slot (ABA) send rejected; direction both ways incl. reply via `envelope.conn()`; congestion rejected at exactly depth 33 with success at exactly 32, recovery after one pop; congestion surfaced through `send_message` as `ConnectionCongested`; envelope delivered byte-exact (payload + conn field); error futures for dead conn/unknown binding; accept-before-connect delivers; disconnect drops queued envelopes (queue gone with mailbox); waiter wake still completes the parked receive.

## 5. Risks & edge cases the coder must handle

1. **Trust-model step-back (MD-2) — accepted, must be disclosed.** Liveness-only arena validation means any task holding a *generation-valid* connection handle sends as that endpoint: direction is caller-identity-based, so a third-party holder is classified as the server side and can deposit into the client's mailbox. The generational slot closes theft-by-recycled-slot (test 4) and nothing else. Disclosure is a Step-H commit-message obligation — a reviewer must not be able to read the diff as ACL-equivalent.
2. **Wait-copy pointer lifetime.** `out_ptr` is a user-stack address inside the *blocked* caller (`ipc_receive_value`'s frame parked inside `raw_syscall`/`wait_future`); the kernel reads it exactly once, after resume, inside the `WaitFuture` arm — never stores it in a future or task. Two coder requirements: bind `let out_ptr = arg2;` before the blocking call (register contents don't survive a context switch; the local does, on the task's kernel stack), and the `out_ptr != 0` guard so `wait_future`'s zero pointer is never dereferenced and non-IPC futures never touch it. Precedent: today's `ReadChar` arm blocks in the same frame and `IpcReadMessage` already writes a user-pointer arg across the syscall boundary.
3. **Register-encoding collisions — exhaustively bounded, not by inspection.** Tagged registers carry only {0, packed-S=256 handle, `IPC_ERR_TAG|code`:1..8}: packed `< 2⁴⁰` (x86_64) / `< 2²⁴` (x86_32) from `free_slots` seeding `0..S` and `HalfSize::MAX` generation (Step-A test 4 asserts the inequality with the same formula). The one *adjacent* space that WOULD collide on x86_32 (bit 24) is `FutureHandle` packed (registry S=1024 ⇒ indices ≥ 256 set bit 24) — neutralized by the invariant that `IPC_ERR_TAG` is decoded ONLY in the connect/bind/send/wait return paths; receive/accept decode bare, wait decodes status. Any future attempt to tag-register a future handle must first shrink or re-encode that space.
4. **`FutureResult`/`into_result` removal blast radius beyond IPC.** Trait impls to edit: `kernel/src/future.rs` (`TimeFuture`, `TaskCompletionFuture`, test `DummyFuture`), `kernel/src/keyboard.rs` (`KeyboardFuture`), `system/src/ipc.rs` (`IpcMessageFuture`); consumers: `kernel/src/syscall.rs` WaitFuture arm (rewritten F), `kernel.rs` (`sleep`/`ReadChar` discard — no edit), usrlib/apps (Steps G/H). `scheduler.rs`/`kernel_services.rs` tests drive futures through the registry (`register`, `notify`, `complete_timer_future`) without naming `into_result` — verified; they stay at 30/1 tests. `boot_and_shell` (item 10) is the non-IPC runtime proof (keyboard future + boot paths); `shell`'s five `pi/snake/tetris/conway/tests` waits (`TaskCompletionFuture`) regress only if the `()` return or `out_ptr` guard is wrong — caught by QEMU hang on item 9's prompt wait.
5. **x86_32 parity.** `Message` is byte-stable across arches (u64 head + `[u8; 56]`, `repr(C)`); the accessors do the `usize`↔`u64` bridge, and the packed ranges shrink consistently; `ipc_err` shifts with `usize::BITS`. No new syscall arg shapes (all ≤ 3 args; `raw_syscall` untouched both arches). Item 8 is the only detector — CI will not catch x86_32 drift.
6. **The 259× integration assertions.** Connection arena (S=256, connect/disconnect slot cycling) untouched ⇒ generation-wrap assertion survives (item 9); per-connection flow never exceeds mailbox depth 1; `"Connection congested"` reaching the shell trips the existing forbidden `"RANDOM Failed to send"` — congestion regression is *armed*, not silently tolerated. Do not "helpfully" retry sends in usrlib to dodge this.
7. **B→F red window.** Four kernel files + one system crate + usrlib re-cut in one tranche; intermediate commits inside the window will not build (Rust cross-crate coupling of the deleted types). Gate strictly at Step F; do not pull any Step-H app edit earlier (the `cargo xtask apps` gate would fail for unrelated reasons).
8. **`TryFrom` desync on deletion.** Deleting a variant without its arm is a compile error (good), but deleting an arm without the variant compiles and silently fails the syscall closed; Step-F target build + grep gate 13 pin both directions.
9. **Congestion is the only send failure — handle it, don't launder it.** `ipc_send` must return `Err(IpcSendError::ConnectionCongested)` to the caller untouched (no in-usrlib spin/retry); `ipc_send_value`'s `?` propagates. Depth check is `== MAILBOX_DEPTH` *before* push (rejects exactly the 33rd; test in Step C pins it).
10. **`send_message` borrow-split.** `connections.borrow(...)` must end before `mailbox_manager.push_back` (disjoint fields of `self` — fine, as today's `create_message` pattern shows); the connection `Handle` compared for direction is `envelope.conn()`, while routing authority is `caller` — do not "simplify" by trusting the envelope to pick the mailbox (that would make MD-2's trust leak steerable by the payload).
11. **`disconnect` teardown order.** `mailbox_manager.remove(client_mailbox)` (drops queued envelopes with the queue) then `connections.remove`; the *server* mailbox is shared per binding and is never drained — dropping another client's queued request there would be a real (not recorded-limitation) data loss.
12. **Stale mixed-ABI artifacts during development.** Old app ELFs on a stale disk image call numbers 18/19/21/24 → fail-closed `0`; always rebuild through `cargo xtask build`/`test --skip-integration` before any QEMU session.
