## M3 — static ISA audit (`cargo xtask check-isa x86_32`, committed with this log)

- New `xtask/src/check_isa.rs`: allow-list classifier over `objdump -d` text.
  Non-instruction lines are skipped by the `addr: ⇥ bytes ⇥ text` shape;
  `lock/rep*/data16/addr16/bnd` prefixes are stripped before the check;
  rejection is anything outside the 386/486 allow-list — the named list of the
  plan plus *any* x87/SSE/MMX or later mnemonic by construction.
- One byte-sensitive rule: objdump decodes `f3 0f bc` as `tzcnt`; that is the
  legacy `rep bsf` fallback LLVM emits without BMI, which executes as `bsf`
  (prefix ignored) on a 486. Allowed only with the `f3` byte prefix; `lzcnt`
  has no such equivalent and is always rejected.
- `nopw`/`nopl` (0F 1F multi-byte padding, availability P6+) are deliberately
  *not* in the allow-list: this tree pads with `0x90` only (measured: all
  nops in kernel + ELFs are `90`), and any future switch to hinted-nop
  padding must trip the gate loudly for a human decision.
- `movsd` is allow-listed as the 386 string move; objdump prints the SSE2
  scalar-double form identically, and the M1 feature pin is what guarantees
  only the string form exists. Audit limitation recorded here, not in code.
- Unit tests: header/padding skip, named-mnemonic rejection, x87/SSE rejection,
  the kernel workhorse list (lock cmpxchg/xadd/decl, tzcnt+f3, pause, rep
  movsl, iret, lgdtl…), tzcnt-without-f3 rejection, lzcnt rejection,
  occurrence aggregation. Green: 8/8 (`cargo test -p xtask`).
  Test-driven fixes during bring-up: AT&T `setcc` is 4 *or* 5 characters
  (`seta`/`setae`), and `movw`/`lgdtl` joined the allow-list — both misses
  caught by the on-tree audit before commit.
- CI: step `ISA audit (486 baseline)` added to the `build-x86_32` job after
  `cargo xtask build x86_32`; the x86_64 job is untouched and the subcommand
  refuses non-x86_32 arches with exit 2.
- On-tree audit: green — `check-isa x86_32: kernel and 21 user ELFs are
  486-clean`, exit 0.
- Poisoned-build trial, measured deviation from the plan's recipe: neither
  `RUSTFLAGS=-C target-cpu=i686` nor `-C target-feature=+cmov` produces `cmov`
  here. Worse-and-better: `RUSTFLAGS` *replaces* the root `.cargo/config.toml`
  `[target.rosx-i686-user] rustflags` (`-Tlinker.ld --pie`), so an exported
  `RUSTFLAGS` links a degenerate, `.text`-less ELF instead of poisoning codegen
  — an operational trap worth knowing (restore with a flagless rebuild), and
  proof that stray CI `RUSTFLAGS` cannot silently break the pin.
  The red signal was therefore demonstrated at the artifact level: a copy of
  `pi` with `f3 0f 44 c1` patched over a `0x90` run in `.text` (objdump
  decoded `repz cmove %ecx,%eax`) made the audit exit 1 naming
  `pi: cmove x1`; restoring the original file made it green again. The
  prefix-stripping path (`repz` → `cmove`) exercised end to end.

## M4 — mmap-less memory detection (`c12c2b5`)

- New `arch/x86-generic/src/multiboot.rs`: Multiboot v1 info decode owning its
  own `BootMemory`/`MemoryRegion` types (deliberately kernel-free: linking
  `kernel` into the host test harness collides with std's
  `alloc_error_handler`, so the decoder keeps zero kernel dependency and
  `arch/x86_32/src/main.rs` adapts regions into `MemoryBlocks`).
- Semantics per plan §6: bit 6 → mmap walk (stride `size + 4`, available-only,
  usize-representable); bit 0 only → `[0, mem_lower KiB)` + `[1 MiB, 1 MiB +
  mem_upper KiB)`; neither → no regions (no invented defaults). mmap wins when
  both flags are set.
- Host unit matrix (`cargo test -p x86-generic`): 26 green (9 new multiboot
  tests — available filtering, stride, empty/truncated buffer, flag precedence,
  zero-size drops, absent flags, malformed entry types).
- QEMU boot after the change: `-cpu 486` reaches `rose>`; `[MEMORY]` banner
  parses the mmap path (Region 0x219be0-0x7fe0000, Total 125 MB), BULK
  self-test green.
- Full x86_32 integration suite re-run: green (M2's run post-dates the M4 tree:
  recorded above covers both).
- The mem_upper fallback path itself stays **unverified** in QEMU (QEMU always
  supplies mmap); routed to M5 checklist item 1.

## Post-plan — D2 hygiene pass: i686 → i486 rename

With the invariant enforced (pin + `-cpu 486` + CI audit), D2's deferred
rename landed: `rosx-i686.json` → `rosx-i486.json`,
`rosx-i686-user.json` → `rosx-i486-user.json` (`git mv`, history preserved),
and all 34 dependent references moved with them: `ArchSpec` fields in both
`xtask` and `tests-integration`, `arch/x86_32/.cargo/config.toml`,
`build.rs`, the nine `include_bytes!` paths in `main.rs`,
`echo-stress.py`, the runner test fixture, both CI workflows' artifact paths,
and the five AGENTS.md spots. Cargo names output directories after the JSON
stem, so artifacts live under `target/rosx-i486*/` from this commit on. The
load-bearing companion: the root `.cargo/config.toml` `[target.rosx-i686-user]`
rustflags key had to be renamed in lockstep — the key matches the target
name, and a stale key drops `-Tlinker.ld` (the degenerate, `.text`-less link
recorded under M3). Verified by rebuilding from a clean target: `.text`
present, boot + `check-isa` + both integration suites + unit suite green.

Deliberately kept: `"llvm-target": "i686-unknown-none"` — the triple names
the 32-bit x86 ABI class as understood by LLVM; the `features` string is the
codegen floor, proven by M1 and guarded by `check-isa`. Dated plan documents
keep their `rosx-i686` references as records of measurements taken at
`50cd060`.

## M5 supplement — 86Box emulator session, emulated i486SX-25 (2026-11-02)

Emulator evidence only. Nothing here marks a hardware checklist item green;
the seven silicon checks stay open. The point of the session was to test the
port on a machine model outside the QEMU `-cpu 486` recipe: a period-typical
486SX board with period-typical firmware, driven headless through the
86box-mcp MCP server (86Box 7.0/master, built with `AUTOMATION=ON` plus a
`GDBSTUB=ON` reconfigure for the boundary probes).

Machine: `486sp3c` = [SiS 496] ASUS PVI-486SP3, Award PCI BIOS dated
06/25/96, `cpu_family=i486sx` at 25 MHz, no FPU, 8 MB RAM, S3 Trio64 PCI,
488 MB IDE disk (993/16/63) plus ATAPI CD-ROM. POST reported
`80486SX CPU at 25MHz` and `Memory Test: 8192K OK`; SETUP reported
`Co-Processor: Not Installed` and `Extended Memory: 7168K`.

Boot media — era findings:

- The 1996 Award BIOS offers `Boot Sequence` C,A only: no El Torito, so the
  CD cannot boot on this board. And GRUB Legacy 0.97-67 cannot reach the
  ATAPI CD as a disk device — a live `grub>` shell on the emulator returned
  `Error 23` for `root (cd)`: 0.97 reads ISOs only through stage2_eltorito's
  own boot info, and that needs the El Torito boot the BIOS lacks. Era
  conclusion: on a board of this vintage the HDD is the authentic RosX boot
  medium; the CD wish stands resolved that way.
- The AGENTS.md hardware recipe executed literally: GRUB Legacy 0.97-67
  (the etch-era build with zero five-86 instructions — the 2022 package is
  not 486-clean, 66 offenders in `stage2_eltorito`) installed by the grub
  shell onto the image's MBR with embedded `fat_stage1_5` over a FAT16
  `/boot`, `kernel /boot/rosx` in `menu.lst`. It boots to `rose>` with the
  full roster; `ls`, `mem`, `ata` probes pass; the `bulk` self-test completes;
  no spontaneous resets (`hard_resets: 1`, that one was mine).

The Multiboot boundary, observed at the kernel's first instruction (GDB-stub
break at `0x101000`, `%eax = 0x2BADB002`):

- GRUB Legacy 0.97-67 passes `%ebx` → MBI with `FLAGS = 0x3E7`,
  `mem_lower = 0x27F` (639 KiB), `mem_upper = 0x1C00` (7168 KiB) — and
  notably it does set the mmap flag (bit 6) with a real five-entry e820 map;
  the extended entry `{0x100000, 0x700000, usable}` matches the BIOS sizes.
  So a stock 0.97 handoff exercises the same `mmap` branch as GRUB 2.
- To drive the checklist-1 scenario ("a GRUB build that lacks the mmap
  buffer") the FLAGS dword was patched to `0x00000001` while the CPU was
  stopped at the entry breakpoint — exactly a v1 MBI carrying only memory
  sizes. The kernel synthesized its heap from `mem_lower`/`mem_upper`
  (`[MEMORY] Region: 0x219be0-0x800000 (6041 KB)`, `Total: 5 MB`), booted
  every service to `rose>`, and `mem` reported the live allocator healthy
  (total 6041 KiB, 2501 KiB free) on that boot. The fallback path works;
  in an emulator.

Timing and silicon-adjacent facts from the same boot: `SYSTEM_TIME_MS`
advanced exactly 1:1 (180 → 1180 over 1000 ms of emulated time) — PIT 100 Hz
through the SiS 496's 8253/8259A plumbing; the emulator itself reports
`no FPU` and the kernel ran FP-free end to end, consistent with the
no-FP-on-32-bit rule; ATAD identified the drive (`86B_HD00`, 1000944
sectors) and the `ata` app read LBA 0 through 16-bit PIO
(`mbr signature 55AA ok`, `part0 boot=80 type=06 lba=63`).

Test assets stayed untracked under `/tmp/opencode/rosx-i486-86box/`
(VM dir with the GRUB-Legacy-installed `hdd.img`, the VM template config,
the era GRUB Legacy El Torito ISO, the GRUB floppy). The GRUB floppy path
also booted the 486SX (stage2 from FAT12, `root (hd0,0)` handoffs work),
demonstrating the A:-fallback chain the primed BIOS gives with C,A order.
